Dynatrace: Giải pháp, kỹ thuật và kiến trúc
Định hướng xây dựng hệ thống Root Cause Analysis (RCA)

Báo cáo phân tích cách Dynatrace thu thập dữ liệu, xây dựng đồ thị phụ thuộc thời gian thực, phát hiện bất thường, gộp sự kiện thành "problem" và xác định nguyên nhân gốc bằng causal AI (Davis). Phần sau chuyển hóa các nguyên lý đó thành phát biểu bài toán, danh mục vấn đề, yêu cầu hệ thống, phương pháp đánh giá kèm baseline so sánh, phương pháp kiểm thử, kiến trúc tham chiếu và một use case thực tế (dịch vụ Cloud Server trên OpenStack) để tự xây một hệ thống RCA.

0.Tóm tắt điều hành

Dynatrace là nền tảng observability "all-in-one" (APM, hạ tầng, log, digital experience, security, business analytics) với điểm khác biệt cốt lõi là RCA tự động, xác định (deterministic) thay vì chỉ tương quan thống kê. Bốn trụ cột kỹ thuật tạo nên khả năng này:

1. OneAgent + PurePath

Một agent duy nhất tự động cài đặt (auto-inject), tự phát hiện process/service, thu thập metric, log, trace code-level (PurePath) và đồng thời tự khám phá topology (ai gọi ai, chạy trên đâu).

2. Smartscape

Đồ thị phụ thuộc thời gian thực gồm node (host, process, service, K8s workload, cloud resource...) và edge có hướng (calls, runs_on, is_part_of...). Đây là "bản đồ nhân quả" mà AI đi trên đó.

3. Grail

Data lakehouse hợp nhất logs, metrics, traces, events, entity, business event trong một kho, truy vấn bằng DQL, schema-on-read, phân vùng theo bucket/retention.

4. Davis AI (causal AI)

Baseline đa chiều tự học → sinh Davis event → gộp event có chung nguyên nhân vào một problem theo thời gian + topology → phân tích fault-tree trên đồ thị để xếp hạng root cause entity và tính blast radius.

Kết luận cho dự án RCA: Thứ tạo nên Dynatrace không phải một mô hình ML "thông minh", mà là mô hình dữ liệu có ngữ cảnh (mọi tín hiệu đều gắn với một entity trong đồ thị phụ thuộc) cộng với bộ luật gộp sự kiện rõ ràng và duyệt đồ thị nhân quả có thể giải thích từng bước. Đây là những thứ có thể tái tạo được với công nghệ mở.

1.Tổng quan giải pháp Dynatrace

1.1 Định vị

Dynatrace tự định vị là nền tảng "AI-powered observability" hướng tới vận hành preventive & autonomous: dùng deterministic AI để phát hiện, giải thích, dự đoán và tự động khắc phục. Nền tảng chạy trên một kho dữ liệu hợp nhất (Grail) và một mô hình phụ thuộc thời gian thực (Smartscape), phục vụ đồng thời nhiều đội (Ops, SRE, Dev, Security, Business).

1.3 Bộ công nghệ lõi (tên thương hiệu)

  • OneAgent: agent hợp nhất trên host, tự inject code module vào process.
  • ActiveGate: proxy bảo mật/định tuyến và điểm thực thi giám sát từ xa (cloud API, K8s API, Prometheus, SNMP, synthetic).
  • PurePath (thế hệ 4): công nghệ distributed trace code-level, hỗ trợ OpenTelemetry và W3C Trace Context.
  • OpenPipeline: lớp ingest/xử lý/định tuyến/làm giàu dữ liệu trước khi vào Grail.
  • Grail: data lakehouse cho observability; DQL là ngôn ngữ truy vấn.
  • Smartscape: đồ thị phụ thuộc thời gian thực (nay lưu trong Grail, truy vấn bằng smartscapeNodes/smartscapeEdges).
  • Davis AI (Dynatrace Intelligence): causal + predictive + generative (Davis CoPilot / Dynatrace Assist) + agentic AI.
  • AppEngine / AutomationEngine: nền tảng app và workflow tự động chạy trên dữ liệu Grail.

2.Kiến trúc tổng thể

2.1 Lớp thu thập: OneAgent, PurePath, OpenTelemetry, cloud

  • OneAgent cài một lần trên host (hoặc DaemonSet/Operator trên K8s). Nó gồm OS agent (host metric, process discovery, network), các code module tự inject vào runtime (Java, .NET, Node.js, Go, PHP, Python...), log module và network module. Không cần sửa code.
  • Nhờ ở trong process, OneAgent thấy được mọi kết nối ra/vào (socket, HTTP, DB, messaging) và tự suy ra service, quan hệ gọi nhau, process chạy trên host nào. Đây là nguồn chính của Smartscape. Trường dt.smartscape_source.sender ghi rõ ai phát hiện entity (osagent, codemodule, zagent...).
  • PurePath là biểu diễn trace end-to-end với thời gian từng span, gắn metadata (status code, method, class, SQL). PurePath 4 hợp nhất span OneAgent và span OpenTelemetry (auto/custom instrumentation), tuân W3C Trace Context để nối trace qua các service do đội khác giám sát.
  • Agentless: ActiveGate gọi cloud API (AWS, Azure, GCP), Kubernetes API, Prometheus, SNMP để lấy metric và khám phá entity/quan hệ không cần agent (VPC, security group, load balancer, K8s object với YAML đầy đủ).
  • External events: CI/CD, ITSM, tool cấu hình gửi event (deployment, configuration change, annotation, custom info) qua API với entitySelector (ví dụ type(HOST),tag(env:prod)) để gắn vào entity. Đây là dữ liệu "what changed" cho RCA.

2.2 OpenPipeline

Lớp xử lý luồng thống nhất trước khi ghi vào Grail. Chức năng chính: nhận dữ liệu mọi định dạng, routing theo điều kiện vào pipeline, processing (parse, mask dữ liệu nhạy cảm, đổi tên trường, trích metric từ log/event, trích business event), gán security context để phân quyền, và gán bucket lưu trữ. Quan trọng với RCA: OpenPipeline làm giàu record với ngữ cảnh topology (entity id, K8s metadata, tag) nên mọi log/metric/event đều truy vết được về một node trong Smartscape.

2.4 Smartscape: đồ thị phụ thuộc thời gian thực

Smartscape classic tổ chức 5 tầng: Applications → Services → Processes → Hosts → Data centers. Quan hệ dọc (vertical) nối các tầng (service chạy trên process nào, process trên host nào); quan hệ ngang (horizontal) là luồng gọi trong cùng tầng (service A gọi service B). Dữ liệu 72 giờ gần nhất; kết nối không có request trong 2 giờ được vẽ nét đứt.

Smartscape mới (on Grail) tổng quát hóa thành đồ thị node/edge đa miền, cập nhật liên tục, truy vấn native graph (multi-hop traverse) trên hàng triệu quan hệ và là "AI-ready context" cho Davis.

3.Mô hình dữ liệu Davis: Event và Problem

Đây là phần đáng tham khảo nhất khi thiết kế hệ RCA vì nó chuẩn hóa "đơn vị bất thường" và "đơn vị sự cố". Trong Grail, cả hai đều là record trong bảng events, phân biệt bằng event.kind.

Davis Event (event.kind = DAVIS_EVENT)

Một bất thường đơn lẻ gắn với một entity: metric vượt ngưỡng, baseline suy giảm, process crash, deployment...

  • event.type: AVAILABILITY_EVENT, PERFORMANCE_EVENT, ERROR_EVENT, RESOURCE_CONTENTION_EVENT, CUSTOM_ALERT, CUSTOM_ANNOTATION, CUSTOM_CONFIGURATION, CUSTOM_DEPLOYMENT, CUSTOM_INFO, MARKED_FOR_TERMINATION, WARNING
  • event.category: INFO, AVAILABILITY, ERROR, SLOWDOWN, RESOURCE_CONTENTION, CUSTOM_ALERT, MONITORING_UNAVAILABLE
  • event.severity: 1 (nặng nhất) → 5
  • event.status: ACTIVE / CLOSED; event.status_transition: CREATED, UPDATED, REFRESHED, TIMED_OUT, RECOVERED
  • dt.smartscape_source.id / .type: entity bị ảnh hưởng
  • dt.davis.is_rootcause_relevant: có được xét làm root cause không
  • dt.davis.is_merging_allowed (dt.event.allow_davis_merge): có được gộp vào problem không
  • event.start / event.end / timestamp (ns UTC)

Davis Problem (event.kind = DAVIS_PROBLEM)

Tập các event có chung nguyên nhân gốc, là đơn vị cảnh báo/ticket duy nhất.

  • display_id (P-2307288), event.id ổn định qua các lần cập nhật
  • event.status: ACTIVE / CLOSED; transition: CREATED, UPDATED, REFRESHED, RESOLVED, REOPENED, CLOSED
  • event.severity = min severity của các event thành viên
  • dt.davis.impact_level: Application, Services, Infrastructure, Environment, Synthetic
  • dt.davis.event_ids: danh sách event thành viên
  • root_cause.smartscape_entity: {id, type, name} của node nguyên nhân
  • smartscape.affected_entities, smartscape.related_entities
  • dt.davis.is_duplicate, duplicate_problem_ids: xử lý trùng lặp
  • dt.duration_marker: mốc thời lượng bậc thang (5 phút, 2 giờ, 7 ngày...)
Nguyên lý: Event là fact gắn entity + thời gian + mức độ; Problem là kết luận gồm tập event, root cause entity, tập entity bị ảnh hưởng và mức tác động. Cả hai bất biến về id, thay đổi trạng thái được ghi thành bản mới (append-only) nên có thể replay lịch sử một problem.

4.Phát hiện bất thường (sinh Davis event)

Dynatrace không dùng một thuật toán duy nhất mà chọn phương pháp theo bản chất tín hiệu. Tất cả đều tạo ra event có cùng schema ở mục 3.

Phương phápÁp dụng choCách tínhChống nhiễu
Multi-dimensional baselining Response time (median & p90), error rate của application/service Học baseline riêng cho từng tổ hợp chiều. Application: user action × geolocation (lục địa→quốc gia→vùng→thành phố) × browser × OS. Service: service method × method group. Ví dụ "USA–New York–Chrome: RT 2s, error 0%, load 2 action/phút". Tính "baseline cube" sau 2 giờ phát hiện, tính lại hàng ngày. Cần ≥ 20% của một tuần dữ liệu mới cảnh báo; đánh giá trong cửa sổ trượt 5 phút (nhanh) và 15 phút (tin cậy hơn); alert kéo dài tối thiểu 5 phút; xét topology trước khi phát cảnh báo.
Prediction-based (seasonal) Traffic / load của application & service (phát hiện sụt/tăng bất thường) Học mẫu ngày/tuần, cần đủ 1 tuần dữ liệu; dự đoán khoảng kỳ vọng rồi so sánh thực tế. Chỉ báo khi lệch khỏi dải dự đoán đủ lâu.
Auto-adaptive threshold Metric hạ tầng và metric tùy ý (CPU, memory, disk, custom) qua metric events Tham chiếu 7 ngày, độ phân giải phút. Baseline = p99; độ dao động = IQR (p25–p75); ngưỡng = baseline + n × IQR (n cấu hình). Cập nhật hàng ngày. Mỗi entity trong scope có ngưỡng riêng (5 host → 5 ngưỡng). Luật vi phạm mặc định 3 phút trong cửa sổ trượt 5 phút (không cần liên tiếp), cửa sổ tối đa 60 phút; có luật de-alert tương ứng. Giới hạn 100 cấu hình metric event / môi trường.
Seasonal baseline (Davis analyzer) Chuỗi thời gian có tính mùa vụ 14 ngày dữ liệu phút; trích mẫu mùa vụ bằng Fourier transform; huấn luyện quantile regression (bền với outlier) với 3 nhóm feature: 10 điểm gần nhất (autoregressive), đặc trưng thời gian/ngày, thành phần mùa vụ. Dự báo one-step-ahead dải tin cậy mỗi phút; tham số tolerance 0.1–10 (mặc định 4). Huấn luyện lại hàng ngày theo từng tuple metric-dimension. Cửa sổ trượt tới 60 phút; fallback về mô hình phân phối đơn giản nếu thiếu dữ liệu, thiếu biến thiên hoặc không có mùa vụ.
Forecast (AutoML) Dự báo dung lượng, disk, SLO, capacity trong workflow/notebook Tự chọn giữa Sampling forecaster (phát hiện mùa vụ giờ/ngày/tuần; mô phỏng 200 đường, 1–1000; trích quantile; cần ≥ 2 giờ cho mẫu giờ, ≥ 7 ngày cho mẫu tuần) và Linear extrapolation (hồi quy tuyến tính, residual chuẩn) làm fallback. Cần ≥ 14 điểm; horizon mặc định 100 (1–600); coverage 0.9. Kiểm tra chất lượng bằng tỉ lệ std dự báo / std đầu vào.
Static threshold Khi cần ngưỡng cố định (SLA, an toàn) Người dùng đặt ngưỡng. Cùng cơ chế cửa sổ trượt.
Point-in-time / availability Process crash, host down, monitoring unavailable, K8s eviction Phát hiện trực tiếp từ agent/K8s event. Không cần baseline.
Nhận xét kỹ thuật: Các thuật toán đều là thống kê cổ điển, giải thích được (percentile, IQR, Fourier, quantile regression, hồi quy tuyến tính). Sức mạnh nằm ở việc baseline theo từng ngữ cảnh (dimension, entity) và luật thời gian (sliding window, minimum duration, learning period) để cắt nhiễu, không phải ở độ phức tạp mô hình.

5.Gộp sự kiện thành Problem (event correlation)

Mục tiêu: một sự cố → một problem, dù nó tạo ra hàng chục event trên nhiều entity. Dynatrace dùng đồng thời ràng buộc thời gian và ràng buộc topology.

5.1 Bộ luật gộp

  1. Cửa sổ 5 phút: event có event.start cách event đầu tiên của problem quá 5 phút sẽ tạo problem mới (trừ khi liên hệ topology được xác nhận trong quá trình phân tích).
  2. Điều kiện topology: chỉ gộp event của các entity có quan hệ phụ thuộc (dọc hoặc ngang) với nhau; "cùng thời điểm" là chưa đủ. Ví dụ Booking gọi Verification: khi Verification chậm kéo Booking chậm, tương quan thời gian thuần có thể đổ lỗi sai cho Booking; kiểm tra edge calls mới cho kết luận đúng.
  3. Xử lý 3 phút: problem mới ở trạng thái processing 3 phút để causal AI quyết định có gộp vào problem khác không, rồi mới alert.
  4. Tuổi 90 phút: sau 90 phút kể từ khi mở, problem không nhận event mới; event mới sinh problem mới (tránh problem "vô tận").
  5. Vòng đời: problem ACTIVE khi còn ít nhất một entity bất thường; event dùng cửa sổ quan sát 3-trong-5 phút để giữ trạng thái active; đóng khi tất cả hồi phục; có thể REOPENED.
  6. Trùng lặp: vì dữ liệu tới bất đồng bộ, có thể sinh 2 problem cho cùng sự cố. Khi dữ liệu muộn tới, problem phụ được đánh dt.davis.is_duplicate=true và gộp. Dynatrace chấp nhận điều này để cảnh báo nhanh nhất thay vì chờ lâu hơn.
  7. Dedup event: event cùng semantic type, cùng nguồn, cùng khung thời gian được gộp thành một event (refresh) thay vì tạo mới.
  8. Cờ điều khiển: dt.event.allow_davis_merge và dt.event.is_rootcause_relevant cho phép nguồn ngoài quyết định event có tham gia gộp/RCA không.

5.2 Mức tác động (impact level)

Problem được gán impact_level theo tầng cao nhất bị ảnh hưởng: Infrastructure < Services < Application (người dùng thật) / Synthetic / Environment. Đây là cơ sở để ưu tiên theo tác động khách hàng thay vì theo severity thô.

6.Thuật toán RCA của Davis (causal AI)

Davis mô tả phương pháp là fault-tree analysis xác định, "cùng phương pháp NASA và FAA dùng", chạy trên đồ thị Smartscape và dữ liệu giao dịch (PurePath). Kết quả có thể tái lập từng bước, khác ML tương quan vốn không cho biết chiều nhân quả.

6.1 Nguyên lý cốt lõi

  • Ngữ cảnh trước, thời gian sau. "Time correlation alone is not sufficient." Hai entity chỉ được coi là cùng problem khi tồn tại đường phụ thuộc giữa chúng trong Smartscape (và với service, có giao dịch thực sự đi qua đường đó trong khung thời gian).
  • Không có độ trễ học. Mô hình ngữ cảnh dựa trên phụ thuộc đã biết (Smartscape, OneAgent, cloud integration), không cần huấn luyện tương quan từ lịch sử. Vì vậy RCA hoạt động ngay với service mới.
  • Fault tree trên đồ thị. Từ triệu chứng ở đỉnh (application/entry service) đi xuống theo calls và runs_on, mỗi nhánh kiểm tra "entity này có bất thường không". Nút bất thường sâu nhất mà không còn nguyên nhân sâu hơn là root cause; các nút phía trên là hậu quả.
  • Ranking. Tất cả bất thường liên quan đều được đưa vào và xếp hạng "contributor"; kết quả trình bày là root cause chính + toàn bộ vertical stack (host → process → service) để người vận hành thấy ngữ cảnh.
  • Change point trên metric. Ngoài event có sẵn, RCA chủ động chạy phân tích metric của các entity trong tập ảnh hưởng để tìm thời điểm thay đổi đột ngột, nhằm bắt nguyên nhân chưa được baseline nào cảnh báo.
  • Event thay đổi là ứng viên hàng đầu. Deployment, configuration change, K8s manifest change, pod eviction (ví dụ do vượt ephemeral storage) gắn với entity trong stack root cause được nêu là nguyên nhân với gợi ý rollback.
  • Giải thích được. Mọi bước gắn với bằng chứng (event, chart baseline, trace, topology); Visual Resolution Path vẽ luồng service và timing từ root cause đến frontend.

6.2 Impact analysis

Chạy song song với RCA, dựng "topology-induced impact tree": từ root cause đi ngược chiều calls/runs_on lên các entry-point service và application; tính số entity ảnh hưởng (blast radius), SLO bị vi phạm, số người dùng thực có thể ảnh hưởng, business flow liên quan. Đây là căn cứ xếp hạng problem trong hàng đợi xử lý.

6.3 Frequent issue detection

Davis nhận diện vấn đề lặp lại theo chu kỳ (ngày/tuần) trên một entity và hạ mức nhiễu: vấn đề "quen" không tạo alert mới ồn ào, nhưng vẫn được ghi để phân tích. Điều này bổ trợ cho baseline tự học, tránh alert storm theo lịch (batch job đêm, backup).

6.4 Giới hạn được tài liệu thừa nhận

  • Chấp nhận thông tin chưa đầy đủ và problem trùng lặp tạm thời để alert nhanh.
  • Chất lượng RCA phụ thuộc độ đầy đủ của topology và event thay đổi được gửi vào; thiếu deployment event thì hệ chỉ chỉ ra entity, không chỉ ra "cái gì đã đổi".
  • Smartscape classic chỉ giữ quan hệ 72 giờ; quan hệ hiếm xảy ra có thể không hiện diện lúc phân tích.

7.Hypermodal AI: predictive + causal + generative + agentic

Predictive

ML/thống kê (AutoML chọn mô hình theo variance, seasonality, trend, noise): baseline, auto-adaptive threshold, seasonal quantile regression, sampling forecaster. Dùng cho anomaly detection, capacity, autoscaling.

Causal

Xác định, dựa trên Smartscape + PurePath + event. Fault tree, ranking root cause, gộp anomaly, blast radius, xếp hạng rủi ro bảo mật, đánh giá tác động kinh doanh.

Generative

Davis CoPilot / Dynatrace Assist: ngôn ngữ tự nhiên → DQL, dashboard, notebook, workflow code; giải thích problem; gợi ý khắc phục. Prompt được làm giàu bởi kết quả causal/predictive và trả lời trên dữ liệu Grail thực nên hạn chế ảo giác.

Agentic AI (preview): các agent dùng kết quả của deterministic AI để đề xuất và thực thi hành động đã được duyệt dưới guardrail chính sách (mở ticket, thông báo, chạy runbook, rollback). Nguyên tắc: LLM không phải nguồn sự thật; nó là lớp giao tiếp và tổng hợp bên trên kết quả xác định.

Áp dụng: Thiết kế RCA của ta nên tách rõ "engine xác định" (baseline, gộp event, duyệt đồ thị) và "lớp LLM" (giải thích, sinh truy vấn, gợi ý). LLM chỉ được nhận input là problem card có cấu trúc và dữ liệu truy vấn được, không tự suy nguyên nhân từ log thô.

8.Bài học thiết kế rút ra cho hệ thống RCA

  1. Entity-first. Mọi tín hiệu (metric, log, trace, event) phải được gắn entity_id ngay lúc ingest. Không có địa chỉ trong đồ thị thì không thể suy nhân quả.
  2. Đồ thị phụ thuộc là hạ tầng bắt buộc, không phải tính năng phụ. Cần nguồn quan hệ thực (trace, K8s API, cloud API, service mesh, CMDB) và cập nhật liên tục với timestamp để truy vấn "topology tại thời điểm T".
  3. Chuẩn hóa Event trước khi nghĩ đến AI. Một schema event thống nhất (type, category, severity, entity, start/end, status, flags) là điểm hội tụ của mọi detector và mọi nguồn ngoài.
  4. Baseline theo ngữ cảnh + luật thời gian. Percentile/IQR/seasonal đơn giản nhưng tính riêng cho từng entity/dimension, kèm sliding window "k-trong-n phút", learning period và minimum duration.
  5. Gộp bằng thời gian AND topology. Luật 5 phút/90 phút/3 phút xử lý là điểm khởi đầu tốt; chấp nhận dedup hậu kỳ để alert nhanh.
  6. RCA = duyệt đồ thị có hướng + xếp hạng, có bằng chứng. Không dùng mô hình hộp đen để chọn root cause. Mỗi kết luận phải chỉ ra đường đi trong đồ thị và event/metric hỗ trợ.
  7. Change events là dữ liệu hạng nhất. Tích hợp CI/CD, GitOps, K8s audit, feature flag, IaC để "what changed" luôn có mặt.
  8. Impact song song với cause. Ưu tiên theo tác động người dùng/business, không theo severity kỹ thuật.
  9. Append-only, replayable. Lưu mọi phiên bản event/problem để audit, đánh giá độ chính xác RCA và huấn luyện luật.
  10. LLM ở lớp trên cùng. Grounding trên problem card và truy vấn dữ liệu; dùng để giải thích, tóm tắt, gợi ý, không để quyết định.

9.Đặt bài toán RCA

Trước khi xây, cần phát biểu bài toán đủ chặt để mọi người hiểu cùng một "root cause" và để có thể đo được. Phát biểu dưới đây mô phỏng cách Dynatrace định nghĩa (event → problem → root cause entity + vertical stack), nhưng viết thành đầu vào/đầu ra tường minh.

9.1 Phát biểu hình thức

Đầu vào (tại thời điểm phân tích t)

  • Đồ thị phụ thuộc G(t) = (V, E): V là tập entity (service, process, host, pod, workload, DB, queue...), E là tập cạnh có hướng, có kiểu (calls, runs_on, is_part_of...) và có hiệu lực theo thời gian.
  • Chuỗi thời gian M = {mv,k(τ)}: metric k của entity v (RT p50/p90, error rate, throughput, CPU, memory, restart...).
  • Tập event Ev = {e = (entity, type, category, severity, start, end, evidence)} gồm event bất thường do detector sinh và event thay đổi (deployment, config, K8s event) từ nguồn ngoài.
  • Trace T: mẫu giao dịch phân tán trong cửa sổ, dùng để xác nhận cạnh calls có lưu lượng thật.

Đầu ra

  • Tập problem P = {Pi}: mỗi Pi là một phân hoạch con của Ev sao cho các event trong cùng Pi có chung nguyên nhân. Mục tiêu: một sự cố thực ↔ một problem.
  • Root cause của Pi: một entity r ∈ V (kèm vertical stack của r) và danh sách contributor xếp hạng [(v1, s1), (v2, s2), ...].
  • Nguyên nhân thay đổi (nếu có): event thay đổi c ∈ Ev được gắn với r hoặc stack của r, giải thích "cái gì đã đổi".
  • Impact: tập entity bị ảnh hưởng, entry point, impact level, ước lượng người dùng/SLO.
  • Bằng chứng: đường đi trong G, event, metric trước/sau cho mỗi kết luận.

9.2 Định nghĩa "root cause" dùng để gắn nhãn và đo

Đây là điểm gây tranh cãi nhiều nhất trong thực tế, nên phải chốt bằng văn bản:

  • Root cause entity: entity bất thường sâu nhất trong chuỗi phụ thuộc mà nếu khắc phục tại đó thì toàn bộ triệu chứng trong problem biến mất. Nếu nhiều entity thỏa (ví dụ host và process trên host đó), lấy entity ở tầng thấp nhất và coi cả vertical stack là đúng.
  • Root cause change: hành động (deploy, config, scale, kill...) xảy ra trước triệu chứng và tác động lên root cause entity hoặc stack của nó. Khi có, đây là câu trả lời "đầy đủ"; khi không có dữ liệu thay đổi, chỉ chấm điểm ở mức entity.
  • Contributor: entity bất thường khác có góp phần làm nặng thêm (ví dụ retry storm) nhưng không phải nguồn.
  • Triệu chứng: entity bất thường chỉ vì phụ thuộc vào root cause. Không được xếp là root cause.
Mức độ chấp nhận khi chấm điểm: dự đoán được coi là đúng ở mức "entity" nếu trùng root cause entity hoặc nằm trong vertical stack của nó (cùng cách Dynatrace trình bày kết quả). Coi là đúng ở mức "change" nếu chỉ đúng event thay đổi. Báo cáo cả hai mức riêng rẽ.

  • Thiếu ground truth: postmortem lịch sử ít, nhãn không thống nhất. Cần đầu tư fault injection và quy trình gắn nhãn (mục 12).
  • Niềm tin và adoption: vài lần RCA sai sẽ khiến đội vận hành bỏ qua. Bắt đầu ở chế độ shadow (gợi ý, không alert), công bố độ chính xác đo được, thu feedback ngay trên problem card.
  • Sở hữu dữ liệu: topology cần đội platform, change events cần đội CI/CD, instrument cần đội phát triển. Phải có chuẩn (naming, resource attributes, event API) và cơ chế bắt buộc ở pipeline.
  • Đa tenant, phân quyền: problem card lộ topology của hệ thống khác. Cần security context ở mức entity như Dynatrace.
  • Chi phí vận hành engine: stream processor, graph store, batch baseline hàng ngày. Cần định cỡ theo số entity, số chuỗi, tốc độ event.

12.Phương pháp đánh giá hệ thống RCA và baseline

Không thể cải tiến thứ không đo được. Phần này định nghĩa: ground truth lấy từ đâu, đo bằng chỉ số gì, so với baseline nào, theo quy trình nào. Thiết kế lấy cảm hứng từ các benchmark RCA cho microservice trong nghiên cứu (RCAEval, PetShop, các bộ dữ liệu trên Sock Shop/Train-Ticket) và từ cách Dynatrace tách "phát hiện" khỏi "nhân quả".

12.1 Ba lớp đánh giá

Lớp 1 Phát hiện & gộp

Lớp 2 Nhân quả

Lớp 3 Giá trị vận hành

12.6 Quy trình đánh giá

  1. Chuẩn bị bộ dữ liệu: chạy fault injection theo kế hoạch phân tầng, lưu toàn bộ telemetry thô (span, metric, log, K8s event, deployment event) và nhãn vào kho đánh giá; bổ sung sự cố lịch sử có nhãn.
  2. Replay offline: vì engine xác định, phát lại telemetry theo event time qua pipeline vào engine với cấu hình cần đánh giá; xuất problem card theo thời gian. Chạy cùng dữ liệu cho B0–B6.
  3. Chấm điểm tự động: script khớp problem với sự cố nhãn (chồng lấn thời gian và entity), tính toàn bộ chỉ số mục 12.3, kèm khoảng tin cậy bootstrap và bảng theo lát cắt.
  4. Ablation: tắt lần lượt topology, change events, change-point on-demand, seasonal baseline để đo đóng góp.
  5. Đánh giá định tính: 20–30 problem card được 2 kỹ sư vận hành chấm về tính giải thích được và hành động gợi ý (thang 1–5).
  6. Shadow mode 4–8 tuần trên production: thu feedback đúng/sai; tính tỉ lệ xác nhận, false positive/ngày, tỉ lệ trùng; so với ticket thực.
  7. Quyết định go/no-go theo tiêu chí mục 12.4 và NFR; sau đó bật alert cho một nhóm dịch vụ, mở rộng dần.
  8. Đánh giá liên tục: mỗi quý chạy lại bộ fault injection (regression), cập nhật bộ nhãn từ postmortem mới, theo dõi Lớp 3 trên dashboard riêng.
Bẫy cần tránh khi đánh giá: (1) chỉ đo AC@1 mà bỏ over-merge, dẫn tới hệ "đúng root cause" nhưng gộp cả hệ thống vào một problem; (2) dùng bộ tune để báo kết quả; (3) chỉ tiêm lỗi ở lá đồ thị (dễ) mà không tiêm ở hạ tầng dùng chung; (4) không ghi lại phiên bản cấu hình detector/engine cùng kết quả, làm mất khả năng so sánh giữa các lần.

13.Phương pháp kiểm thử hệ thống RCA

Mục 12 trả lời "hệ tốt đến đâu"; mục này trả lời "làm sao biết hệ chạy đúng như thiết kế, và không hỏng khi sửa". Điểm thuận lợi lớn: engine RCA là xác định (cùng đầu vào cho cùng đầu ra), nên có thể kiểm thử như phần mềm thông thường bằng dữ liệu cố định và kết quả kỳ vọng, thay vì chỉ đo thống kê.

13.1 Kim tự tháp kiểm thử cho RCA

13.2 L0: Bộ sinh dữ liệu tổng hợp và fixture

Đây là khoản đầu tư quan trọng nhất cho kiểm thử. Một công cụ nội bộ (CLI/thư viện) sinh ra bộ dữ liệu đầy đủ từ một kịch bản khai báo, để mọi tầng kiểm thử dùng chung định dạng.

# scenario: db_slow_cascades_to_frontend.yaml
topology:
  nodes: [frontend, checkout, payment, orders-db, node-1, node-2]
  edges:
    - [frontend, calls, checkout]
    - [checkout, calls, payment]
    - [checkout, calls, orders-db]
    - [checkout, runs_on, node-1]
    - [payment, runs_on, node-2]
    - [orders-db, runs_on, node-2]
normal:                      # hành vi nền 7 ngày
  rt_ms: {frontend: 120, checkout: 60, payment: 40, orders-db: 8}
  error_rate: 0.002
  seasonality: daily        # đỉnh 10h-16h
faults:
  - at: "day7 10:00"  duration: 12m
    target: orders-db  type: latency  factor: 8
    propagate: upstream       # checkout, frontend chậm theo
change_events:
  - at: "day7 09:58"  target: orders-db
    type: CUSTOM_CONFIGURATION  note: "max_connections 200->50"
noise:
  clock_skew_s: {node-2: 1.5}
  ingest_delay_s: {payment: 90}
expected:
  problems: 1
  root_cause: orders-db          # hoặc stack [orders-db, node-2]
  root_cause_change: "max_connections 200->50"
  impacted: [checkout, frontend]
  not_root_cause: [payment, node-1]
  ttd_max: 4m

Đầu ra của bộ sinh:

  • Span OTLP với trace context nối đúng theo cạnh calls, RT/error theo phân phối cấu hình, có mùa vụ và nhiễu.
  • Metric theo phút cho mọi entity (RED, CPU, memory) khớp với span.
  • K8s object/event, deployment event theo change_events.
  • Đồ thị kỳ vọng (nodes/edges) để so với topology builder.
  • File expected để chấm tự động.

Yêu cầu với bộ sinh: có seed để tái lập; mô phỏng được lan truyền lỗi theo chiều gọi (upstream chậm khi downstream chậm, có độ trễ và suy giảm), retry storm, noisy neighbor qua cạnh runs_on; tiêm được nhiễu thực tế (lệch đồng hồ, dữ liệu tới muộn, mất mẫu, sampling).

Fixture chuẩn: bộ 30–50 kịch bản nhỏ được commit vào repo làm hợp đồng hành vi; mọi thay đổi engine phải chạy lại toàn bộ.

13.4 L2: Kiểm thử thành phần và tích hợp

  • Pipeline enrichment: đưa OTLP với resource attributes mẫu (đủ, thiếu, sai tên) → kiểm tra entity_id gán đúng, record thiếu vào hàng đợi unresolved, PII được mask, event time và ingest time đều có.
  • Topology builder: nạp span từ kịch bản L0 → so đồ thị sinh ra với đồ thị kỳ vọng (precision/recall cạnh phải 100% trên dữ liệu sạch; với sampling 10% vẫn ≥ 95% cạnh có lưu lượng đáng kể); kiểm tra TTL, cạnh dọc từ K8s object, hợp nhất entity trùng.
  • Detector trên chuỗi tổng hợp: chuỗi có mùa vụ 14 ngày + bất thường tiêm tại thời điểm biết trước → event mở trong ≤ 3 phút, không event trong 14 ngày nền (false positive = 0 trên dữ liệu sạch, ≤ ngưỡng cho dữ liệu có nhiễu).
  • Hợp đồng schema: mọi event/problem xuất ra được kiểm tra bằng JSON Schema có version; thay đổi schema phải kèm migration test.
  • Tích hợp ngoài: API nhận deployment event (hợp lệ, thiếu entity selector, selector không khớp), webhook thông báo (một problem → một thread, cập nhật không tạo thông báo mới), ITSM ticket.
  • Kháng lỗi: tắt engine 10 phút rồi bật → bắt kịp từ Kafka, không mất/không trùng event; dữ liệu đến trễ 3 phút → problem trùng được đánh is_duplicate và gộp.

13.5 L3: Kiểm thử hồi quy bằng replay (golden tests)

Mỗi kịch bản (tổng hợp ở L0 hoặc telemetry thật đã ghi lại) được phát lại qua engine; kết quả (danh sách problem, root cause, contributor, impact, timeline) so với golden output đã duyệt.

  1. Kho kịch bản gồm: fixture tổng hợp, mọi ca fault injection đã chạy (mục 12.2 A), và sự cố production đáng chú ý (đặc biệt các ca RCA từng sai, sau khi sửa phải có test giữ).
  2. So khớp có dung sai: root cause đúng ở mức entity hoặc stack; thời gian mở problem ±1 phút; tập impact so theo Jaccard ≥ 0,9. Khác biệt lớn hơn → fail, in diff đọc được.
  3. Chạy trong CI mỗi pull request cho fixture nhỏ (phút), chạy đêm cho toàn kho (giờ). Kết quả tổng hợp thành bảng AC@k, over-merge theo phiên bản để thấy xu hướng.
  4. Khi thay đổi cố ý (đổi trọng số ranking), cập nhật golden qua quy trình duyệt, không cập nhật tự động.
  5. Kiểm thử tính xác định: chạy replay 3 lần, so byte-level problem card (trừ trường timestamp sinh); khác nhau → fail.

13.6 L4: Kiểm thử đầu-cuối bằng fault injection

Môi trường

  • Cụm Kubernetes riêng cho kiểm thử, chạy ứng dụng mẫu nhiều service (Sock Shop, Train-Ticket, OpenTelemetry Demo) và/hoặc bản sao thu nhỏ hệ thống thật, có load generator tạo lưu lượng nền có mùa vụ (k6, Locust).
  • Toàn bộ stack RCA (collector, pipeline, store, engine, UI) triển khai như production, cấu hình như production.
  • Công cụ tiêm lỗi: Chaos Mesh hoặc LitmusChaos (pod kill, network delay/loss/partition, CPU/memory stress, IO delay, DNS lỗi, time skew), stress-ng trên node, script deploy phiên bản lỗi (Argo CD/Helm), thay đổi ConfigMap/limits.
  • Thời gian nền trước khi tiêm: ít nhất 7 ngày để baseline học (hoặc nạp sẵn baseline từ dữ liệu tổng hợp để rút ngắn).

13.8 L5–L6: Shadow, canary và kiểm thử trên production

  • Shadow mode: engine chạy trên dữ liệu production thật nhưng không thông báo; so problem sinh ra với incident/ticket thật hàng tuần; người trực đánh dấu đúng/sai. Tiêu chí ra khỏi shadow theo mục 12.4.
  • Canary theo nhóm dịch vụ: bật thông báo cho một nhóm dịch vụ ít rủi ro; theo dõi false positive/ngày, tỉ lệ xác nhận; mở rộng theo từng nhóm.
  • Game day có kiểm soát: định kỳ (hàng quý) tiêm lỗi đã duyệt vào production ở giờ thấp điểm với kill switch; đo TTD, AC@1, thời gian điều tra của người trực có và không có problem card (A/B giữa hai kíp).
  • Phiên bản song song: khi nâng engine, chạy phiên bản mới ở chế độ shadow bên cạnh phiên bản cũ trên cùng luồng dữ liệu, so kết quả (diff problem/root cause) trước khi chuyển.
  • Kill switch và rollback: kiểm thử định kỳ việc tắt thông báo toàn cục và quay về phiên bản trước trong ≤ 5 phút.

13.9 Kiểm thử phần trợ lý ngôn ngữ tự nhiên (nếu có)

  • Bộ câu hỏi chuẩn với câu trả lời kỳ vọng dựa trên problem card cố định; chấm bằng người và bằng LLM-judge có rubric (đúng sự thật, có trích dẫn evidence id, không suy diễn ngoài dữ liệu).
  • Kiểm thử "không bịa": problem card thiếu change event → trợ lý phải nói không có dữ liệu thay đổi, không đoán nguyên nhân.
  • Kiểm thử truy vấn sinh ra: DQL/SQL phải chạy được, chỉ đọc, đúng khung thời gian và entity của problem.
  • Kiểm thử an toàn: câu hỏi cố ý đưa chỉ dẫn trong log (prompt injection) không làm trợ lý thay đổi root cause hay thực thi hành động.

14.3 Thuật toán RCA đề xuất (phiên bản có thể triển khai)

1
Sinh event Detector theo entity phát event khi luật k-trong-n phút vi phạm (mặc định 3/5). Event cùng type+entity còn ACTIVE thì REFRESH thay vì tạo mới. Event đóng khi hồi phục đủ m phút (de-alert).
2
Gộp thành problem (correlator) Với mỗi event mới E(entity e, start t): tìm problem ACTIVE P có tuổi < 90 phút mà (a) |t − P.first_start| ≤ 5 phút HOẶC (b) tồn tại đường trong đồ thị tại thời điểm t giữa e và một entity của P với độ dài ≤ L (ví dụ 3 hop, chỉ theo calls/runs_on/is_part_of). Nếu nhiều P thỏa, chọn P có kết nối topology mạnh nhất; nếu không có, mở P mới ở trạng thái PROCESSING 3 phút. Sau 3 phút, nếu P mới kết nối được với P khác thì gộp và đánh is_duplicate.
3
Xây fault tree Lấy tập entity ảnh hưởng A = entity của mọi event trong P. Mở rộng theo chiều phụ thuộc xuống dưới (từ x đi theo calls ra downstream, runs_on xuống process/host/pod, is_part_of lên workload/node) tới độ sâu D. Với entity mới không có event, chạy change-point detection on-demand (ví dụ CUSUM/PELT hoặc so sánh cửa sổ trước/sau với ngưỡng z) trên metric vàng (RT, error, throughput, CPU, mem, restart) trong [P.start − 15', now]; nếu có change point thì thêm event suy diễn (severity thấp, source=rca_probe).
4
Xếp hạng root cause Điểm của entity x = w1·(độ sâu trong cây: càng ở "dưới/downstream" càng cao) + w2·(sớm nhất về thời gian) + w3·(severity/category: availability > resource > error > slowdown) + w4·(có change event: deployment/config/K8s eviction trong [P.start − 30', P.start + 5']) + w5·(số entity phía trên phụ thuộc vào x mà cũng bất thường) − w6·(x có nguyên nhân sâu hơn cũng bất thường). Root cause = x có điểm cao nhất; trình bày cùng vertical stack của x. Giữ danh sách contributor xếp hạng.
5
Impact tree Từ root cause đi ngược chiều phụ thuộc lên các entry-point service/application; tính blast radius, SLO liên quan, ước lượng người dùng/request bị ảnh hưởng, business flow gắn tag. Gán impact_level = tầng cao nhất.
6
Problem card JSON có cấu trúc: root cause, stack, danh sách contributor với bằng chứng (event, metric trước/sau, change event, đường đi trong đồ thị), impact, timeline, hành động gợi ý (rollback deployment X, scale workload Y, xem log query Z). Ghi phiên bản mỗi lần cập nhật.
7
Lớp LLM (tùy chọn) Nhận problem card + quyền truy vấn store để: viết tóm tắt tiếng Việt cho người vận hành, sinh truy vấn log liên quan, đề xuất runbook. Không được thay đổi root cause đã tính; mọi câu trả lời phải trích dẫn evidence id.
8
Vòng phản hồi Người dùng đánh dấu root cause đúng/sai, chọn contributor đúng. Dùng để hiệu chỉnh trọng số w1..w6, độ sâu D, hop L và tham số detector; đồng thời làm bộ dữ liệu đánh giá precision/recall RCA.

15.Use case thực tế: RCA cho dịch vụ Cloud Server trên Public Cloud (backend business + OpenStack)

Áp dụng toàn bộ nguyên lý ở các mục trước vào một bài toán cụ thể: dịch vụ Cloud Server (máy chủ ảo bán cho khách hàng) trên Public Cloud. Lớp backend business (portal, API, đặt hàng, provisioning, billing, quota) gọi xuống OpenStack (Keystone, Nova, Neutron, Cinder, Glance, Placement) và OpenStack điều khiển hạ tầng vật lý (hypervisor KVM, Ceph, OVN/OVS, RabbitMQ, MariaDB Galera). Đặc thù IaaS khác microservice web thuần ở ba điểm: luồng bất đồng bộ qua message queue, quan hệ nhiều-nhiều giữa VM khách và hạ tầng dùng chung, và sự cố hạ tầng vật lý là nguyên nhân phổ biến.

15.5 Detector và event cho miền IaaS

  • Business flow SLI: success rate và time-to-ACTIVE của "Create Cloud Server" theo AZ và flavor, baseline đa chiều (AZ × flavor group), vi phạm 3/5 phút. Đây là event "triệu chứng đỉnh" tương đương application event của Dynatrace.
  • Backend: RT/error theo endpoint (auto-adaptive), pod restart, Kafka lag, Postgres connection saturation.
  • OpenStack API: 5xx rate và RT theo (service, resource, method) từ HAProxy/API log; MessagingTimeout count từ log; service state down từ exporter (availability event); số instance ERROR mới/phút theo AZ và theo lỗi (NoValidHost, PortBindingFailed, BuildAbort).
  • Notification → event: mọi *.error notification thành ERROR_EVENT gắn instance và host; compute.exception thành event trên hypervisor; live migration/evacuate thành CUSTOM_INFO (change event).
  • RabbitMQ: partition (availability), queue depth/unacked auto-adaptive theo queue, memory alarm (static), connection churn.
  • Galera: wsrep_cluster_size < 3 (availability), flow control paused > ngưỡng, slow query, connections saturation.
  • Ceph: HEALTH_ERR/WARN (availability với phân loại), OSD down/out, PG degraded/undersized, op latency auto-adaptive theo pool, pool full ratio static 85/95%.
  • Hypervisor: CPU steal, load/nCPU, memory pressure, IO wait, NIC errors auto-adaptive theo host; nova-compute service down; libvirt không phản hồi; số VM trên host thay đổi đột ngột (evacuate).
  • VM khách: không alert từng VM cho khách (quá nhiều), nhưng tính metric tổng hợp theo hypervisor: tỉ lệ VM có CPU steal > X, IO wait cao; VM state chuyển ERROR/SHUTOFF bất thường thành event gắn VM và hypervisor.
  • Mạng: ovn-controller/agent alive, SB DB lag, port binding failed count, gateway failover event, switch port link down/CRC (T6).
  • Vật lý: IPMI SEL critical, ECC uncorrectable, SMART fail, PSU lost, nhiệt độ: availability/warning event gắn SERVER, tự động lan lên HYPERVISOR qua same_as.
